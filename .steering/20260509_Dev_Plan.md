## 1. プロジェクト方針

### 1.1 プラットフォーム定義

| プラットフォーム | 役割 | 技術スタック |
|----------------|------|------------|
| **iOS版** | **メインプロダクト**。最終的にApp Storeでリリースする成果物 | Swift / SwiftUI / MapKit / Apple Intelligence |
| **Web版** | **先行実装・検証版**。iOS開発前に人に試してもらうための中間成果物。UX・機能設計を固める目的 | Next.js 15 / TypeScript / Mapbox GL JS / Supabase |

> Web版はあくまで「試用・検証」目的の先行版であり、最終プロダクトではない。
> iOS版でほぼ全機能を移植・再実装することを前提に設計する。

### 1.2 除外機能（Web版スコープ外）

以下は **Web版には実装しない**。iOS版（Phase I〜J）で検討する。

| 機能 | 理由 |
|------|------|
| DM（ダイレクトメッセージ） | コミュニケーション機能はiOS版の完成度で提供 |
| フォロー/フォロワー | ソーシャルグラフはiOS版で設計 |
| デジタルカード生成 | ゲーミフィケーション要素はiOS版以降 |
| 物理カード発送 | 印刷API連携は Phase J 以降 |
| リアルタイムカメラAR | Web版での実装が複雑すぎる |

### 1.3 開発体制

| 項目 | 内容 |
|------|------|
| 開発体制 | 1人開発（Claude Code を活用） |
| 開発時間 | 副業・プライベートの空き時間 |
| スキルレベル | React/Next.js/Swift 未経験。Claude と共に学習しながら進める |
| 開発ルール | 1ファイルずつ作成・確認。コミットは開発者が実行 |

## 4. Phase B：認証基盤【最重要・高複雑度】

### 概要

現在の `device_id`（`localStorage` + `crypto.randomUUID()`）ベースのユーザー識別を、Supabase Auth（JWTベース）に移行する。これが完了しないと Phase C 以降のすべての「自分のデータ」系機能が作れない。

**見積もり: 約2週間（1日1〜2時間の作業ベース）**

> ⚠️ **重要**: 多くのファイルに影響する。着手前に必ず設計ドキュメント（`.steering/YYYYMMDD-auth-migration/`）を作成して確認を取ること。

### タスク一覧

| # | タスク | 内容 | 複雑度 | 依存 |
|---|--------|------|--------|------|
| B-1 | Supabase Auth クライアント設定 | `@supabase/ssr` 導入、ブラウザ用・サーバー用クライアントをAuth対応に更新 | 中 | なし |
| B-2 | ログイン・サインアップ画面 | `/auth/login`・`/auth/register` ページ作成（メール/パスワード認証） | 中 | B-1 |
| B-3 | Auth コールバックルート | `/auth/callback` ルート・OAuth対応準備 | 低 | B-1 |
| B-4 | `useCurrentUser` フック統一 | 全コンポーネントで同一フックを使うよう整理。`getOrCreateUser.ts`を廃止 | 中 | B-1 |
| B-5 | ミドルウェア（保護ルート） | 未認証ユーザーを `/auth/login` にリダイレクト | 中 | B-1 |
| B-6 | device_id → auth.uid() 移行 | **最重要**。DBマイグレーション + 全呼び出し元のコード修正 | **高** | B-4, B-5 |
| B-7 | RLS（行レベルセキュリティ）適用 | 全テーブルにポリシー設定。本番適用前にローカルで十分テスト | **高** | B-6 |
| B-8 | プロフィール初期設定画面 | `/setup-profile`。初回ログイン時に匿名ネーム・アバターを設定 | 中 | B-7 |

### 主要な移行ポイント

```
現在:
  localStorage に device_id を保存
  → getOrCreateUser(deviceId) でユーザー取得
  → 全クエリで user_id = device_id で検索

移行後:
  supabase.auth.getUser() でログインユーザーを取得
  → useCurrentUser() フックに統一
  → 全クエリで user_id = auth.uid() で検索
  → 既存データは device_id → auth.uid() に紐付け
```

### 影響ファイル（事前把握）

- `apps/web/lib/user/getOrCreateUser.ts` — 廃止
- `apps/web/lib/user/useCurrentUser.ts` — 大幅改修
- `apps/web/lib/supabase/client.ts` — Auth対応クライアントに更新
- `apps/web/lib/supabase/server.ts` — SSR用Auth対応クライアント追加
- `apps/web/components/map/MapView/MapView.tsx` — useCurrentUser に切り替え
- `apps/web/components/post/PostForm/PostForm.tsx` — useCurrentUser に切り替え
- `apps/web/components/spot/CheckInButton/CheckInButton.tsx` — 同上
- `apps/web/components/oshi/AddOshiForm/AddOshiForm.tsx` — 同上
- `apps/web/lib/supabase/checkins.ts` — 同上
- `apps/web/lib/supabase/spots.ts` — 同上

### 完了基準

- [ ] メール/パスワードでログイン・ログアウトができる
- [ ] 未認証状態で `/` にアクセスするとログイン画面にリダイレクトされる

### 概要

知らないスポットを発見できる検索機能と、趣味の近いユーザーが推しているアイドルのレコメンド機能を実装する。

### タスク一覧（推しレコメンデーション）⭐

| # | タスク | 内容 | 複雑度 |
|---|--------|------|--------|
| E-4 | PostgreSQL 関数 `get_recommended_spots` 作成 | 協調フィルタリングSQL。`user_oshis` テーブルを使い類似ユーザーを集計し、未登録推しのスポットをスコア付きで返す | 中〜高 |
| E-5 | マップへの「おすすめスポット」表示 | レコメンドスポットを特別ピン（別色 or キラキラアイコン）でマップに表示 | 中 |
| E-6 | レコメンド理由テキスト | ポップアップに「同じ好みの N 人が推しています」を表示 | 低 |

### レコメンドアルゴリズム設計（SQL概要）

```
① 自分の推しリスト（user_oshis where user_id = me）を取得
② その推しと重なりがある他ユーザーを集計（類似ユーザー）
③ 類似ユーザーが推している、かつ自分が未登録の推しをスコアでランキング
④ 上位 5 件の推しのスポット（is_public = true）をマップに表示
```

詳細な SQL は `OSHIATO_API_Specification_v5_1.md` の「セクション 9」を参照。

## 8. Phase F：推しの言葉オーバーレイ

### 概要

スポットに登録された「推しの言葉」が、そのスポットに近づいたとき画面に降ってくる体験。スポット詳細写真に言葉を合成してダウンロードする機能も提供する。

**見積もり: 約2週間**

### タスク一覧

| # | タスク | 内容 | 複雑度 |
|---|--------|------|--------|
| F-1 | `spot_quotes` テーブル確認・マイグレーション | DBスキーマ v6.0 で定義済み。実際にマイグレーションを実行する | 低 |
| F-2 | 投稿フォームへの言葉入力欄追加 | `PostForm` に「推しの言葉を残す（任意・100字以内）」フィールドを追加 | 低 |
| F-3 | 近接検知実装（`watchPosition`） | `navigator.geolocation.watchPosition()` でリアルタイム監視。Haversine公式で半径50m以内を検知 | 中 |
| F-4 | 言葉が降ってくるアニメーション | CSS `@keyframes` + `transform: translateY` で文字が上から降ってくる演出。複数の言葉が時間差で流れる | 中 |
| F-5 | 写真へのテキスト合成（Canvas API） | スポット詳細の写真に言葉をオーバーレイ表示し、`toDataURL()` でダウンロード可能に | 中 |
| F-6 | オーバーレイ ON/OFF トグル | スポット詳細ページにトグルスイッチを設置。OFF時は元の写真のみ表示 | 低 |
| F-7 | プリセット言葉の初期登録 | 汎用フレーズ（「ここにいたんだね」「また来たよ」等）をDBに投入 | 低 |

### 技術詳細メモ

| 技術 | 実装方針 |
|------|---------|
| 近接検知 | `watchPosition()` で連続位置取得。Haversine公式でスポット座標との距離を計算。50m以内でイベント発火 |
| アニメーション | CSS `@keyframes` で `translateY(-100vh)` に向けて動かす。複数の言葉を `animation-delay` で時間差 |
| Canvas合成 | `drawImage(img, 0, 0)` → `fillText(quote, x, y)` → `canvas.toDataURL('image/png')` → `<a>` タグで download |
| スコープ | Web版はリアルタイムカメラARは実装しない。写真への合成（静止画）を優先 |

### 完了基準

- [ ] 投稿時に言葉（100字以内）を登録できる
- [ ] スポット詳細ページで登録された言葉の一覧が見られる
- [ ] スポットに50m以内に近づくと言葉が降ってくるアニメーションが発火する
- [ ] スポット詳細の写真に言葉を合成した画像をダウンロードできる
- [ ] オーバーレイ ON/OFF のトグルが動作する

## 11. Phase I：iOS版（メインプロダクト）

### 概要

Web版で検証した全機能をiOSネイティブに移植する。これが最終的にApp Storeでリリースする成果物。

**見積もり: 約4〜6週間（Swift/SwiftUI の学習コスト込み）**

> Phase H 完了後に着手。それまでに Swift/SwiftUI の基礎学習を並行して進めておくと良い。

### 移植対象（Web版の全機能）

| 機能 | Web技術 → iOS技術 |
|------|----------------|
| マップ | Mapbox GL JS → MapKit |
| 認証 | Supabase Auth（共通） |
| 投稿フォーム | React Form → SwiftUI Form |
| EXIF抽出 | `exifr` ライブラリ → `PHAsset` / `Photos.framework` |
| 画像処理 | Canvas API → `UIImage` + `CGContext` |
| 近接検知 | Web Geolocation API → `CLLocationManager` |
| 言葉アニメーション | CSS @keyframes → SwiftUI `Animation` |
| Canvas合成 | Canvas API → `UIGraphicsImageRenderer` |
| DB/API | Supabase JS → Supabase Swift SDK |

### Phase I 固有の追加機能

#### 重複投稿マージ ⭐（iOS限定）

| 項目 | 内容 |
|------|------|
| 目的 | 異なるユーザーが同じ場所を投稿した場合に自動検知して統合を提案 |
| OCRエンジン | `Vision.framework` の `VNRecognizeTextRequest`（On-Device処理） |
| 照合方法 | 写真内テキストをハッシュ化し、`post_images.ocr_text_hash` と照合 |
| 判定閾値 | テキスト一致率 80% 以上で「同じ場所の可能性」として確認を促す |
| マージ動作 | 元投稿に訪問者として追加、写真は別エントリとして紐付け |
| プライバシー | On-Device処理のためサーバーに生テキストを送信しない |
| iOS要件 | iOS 18以降（Apple Intelligence 対応端末） |

#### DM機能（Phase J で計画、Phase I で設計のみ）

- DM機能・フォロー機能はiOS版のリリース後（Phase J）に追加を検討
- DBスキーマ（`dm_rooms`, `dm_messages` テーブル）は v6.0 で定義済み

## 14. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| **Phase B の device_id 移行が多数ファイルに影響** | 既存機能が壊れる | `useCurrentUser` フックに集約してから1ファイルずつ移行。移行期間中は device_id と auth.uid() の両方をサポート |
| **RLS ポリシー適用後にクエリが壊れる** | 全機能が使えなくなる | ローカル Supabase（`supabase start`）で十分テストしてから本番適用 |
| **Swift/SwiftUI の学習コスト過大** | Phase I が大幅遅延 | Web版完成後から本格的に学習開始。基礎が難しければ React Native（Web技術が流用可能）への切り替えを検討 |
| **推しレコメンデーションのデータ不足** | アルゴリズムが機能しない | 初期ユーザーが少ない段階はレコメンドを非表示にするフォールバックを実装 |
| **言葉オーバーレイのアニメーション負荷** | スマートフォンで処理重い | CSS アニメーションを `will-change: transform` で最適化。同時表示言葉数を上限 5 件程度に制限 |
| **Supabase 無料枠の超過** | 追加コスト発生 | 開発中は不要データを定期削除。本番運用開始前に Pro プランへ移行 |
| **Mapbox 無料枠の超過** | 追加コスト発生 | 50,000 tile loads/月を監視。超過前に Mapbox Pro に移行 |
| **1人開発の燃え尽き** | 開発停止 | Phase ごとに完了を祝う。完璧を求めない。Phase G・H は後回し可 |
