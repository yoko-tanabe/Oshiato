## 1. プロジェクト概要

### 1.1 コンセプト

**「推しの足跡を現実世界で見つけ、記録し、辿る」**

OSHIATOは、アイドルファン（推し活層）向けの動的情報マップ＆推し活ログアプリです。OOH広告（屋外広告）やポップアップ（コラボカフェ等）など、期間限定で出現する「推しスポット」をユーザー同士で共有し、訪問記録を「光る足跡」と「色の糸」で可視化します。

### 1.2 ビジョン

- 推し活の「聖地巡礼」体験をデジタルで拡張
- ファン同士の緩やかな繋がりを創出
- 訪問の軌跡を美しく可視化し、思い出として残す

### 1.3 ターゲットユーザー

| セグメント | 特徴 |
|------------|------|
| **メイン** | 20〜40代のアイドルファン（国内） |
| **サブ** | K-POPファン、アニメファン、声優ファン |
| **将来** | 訪日外国人ファン |

### 1.5 リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| **学習コストが想定以上** | 開発遅延 | Claude Codeで都度解説を受けながら進める。無理せず段階的に学ぶ |
| **Swift学習が困難** | Phase 2遅延 | React Nativeへの切り替えを検討（Webの知識が流用可能） |
| **Supabase無料枠超過** | 追加コスト | 開発中は不要データを削除。本番前にPro移行 |
| **Mapbox無料枠超過** | 追加コスト | 開発中はテストを最小限に。50,000 loads/月を監視 |
| **iOS審査リジェクト** | リリース遅延 | 審査ガイドラインを事前確認。プライバシーポリシー準備 |
| **1人開発の限界** | 燃え尽き | MVP機能を絞る。完璧を求めない。Phase 4は状況を見て判断 |
| **セキュリティ問題** | データ漏洩 | RLSを徹底。個人情報は最小限。EXIFは抽出後削除 |
| **データ消失** | 復旧困難 | Supabaseの自動バックアップ活用。Gitでコード管理 |

| No | 機能 | 優先度 | 説明 |
|----|------|--------|------|
| 1 | `spot_quotes`テーブル追加 | 必須 | スポットに紐づく言葉を格納 |

**実装方針:**
- 近接検知: `navigator.geolocation.watchPosition()` + Haversine距離計算

- Canvas合成: `drawImage()` → `fillText()` → `toDataURL()` でダウンロード
- Web版はリアルタイムカメラARは複雑なため「スポット詳細写真への合成」を優先

### 3.9 Phase I: iOS版（最終フェーズ）

**方針:** Web版で検証した全機能をiOSネイティブに移植する。

| No | 機能 | 優先度 | 説明 |
|----|------|--------|------|
| 1〜 | Web版の全機能をiOSに移植 | 必須 | Swift/SwiftUI/MapKitで再実装 |
| + | **重複投稿の自動マージ** ⭐ | 高 | Apple Intelligence On-Device OCRで写真内テキストを認識し、同一スポットを検知してマージ |

**重複投稿マージ（iOS限定）:**
- `Vision.framework`の`VNRecognizeTextRequest`で写真内テキストをOCR
- 抽出テキストをハッシュ化し、既存スポットの`ocr_text_hash`と照合
- 一致率が閾値（例: 80%）以上なら同一場所として確認を促す
- マージ時: 元投稿に訪問者として追加、写真は別エントリとして紐付け
- On-Device処理でプライバシーを保護

**完了基準:**
- iPhoneシミュレータ/実機で全機能動作
- Web版と同じデータを参照・投稿可能

#### 4.2.2 EXIF情報の活用

写真のEXIF情報から、推しの足跡の位置と訪問日時を自動抽出します。

| EXIF項目 | 抽出 | 用途 |
|----------|------|------|
| **GPS座標** | ✅ | スポット位置の自動入力、軌跡マップの精度向上 |
| **撮影日時** | ✅ | 「いつ推しの足跡にあったか」の正確な記録 |
| **カメラ情報** | ❌ | 使用しない |

**処理フロー:**
1. ユーザーが写真を選択
2. EXIF情報（GPS座標・撮影日時）を抽出
3a. GPS座標あり → スポット位置として自動設定
3b. GPS座標なし → LocationPickerを表示（住所検索 or 地図タップで手動指定）
4. 抽出したデータをDBに保存（本人のみ閲覧可能）
5. 画像からEXIFを削除してアップロード（公開用）

**活用シーン:**
- 投稿時に位置・日時を自動入力
- 軌跡マップで「実際にいた時刻」を正確に表示
- 思い出の振り返り「2026年3月21日 14:30、渋谷で推しAの広告に出会った」

#### 4.2.3 プライバシー保護

- 公開される画像からはEXIF情報を完全削除
- 抽出したGPS座標は本人のみ閲覧可能（RLSで保護）
- 匿名ネームで投稿（本名は非公開）
- 公開される位置情報はスポット単位のみ（個人の撮影位置は非公開）

### 4.4 推しレコメンデーション機能（Phase E）⭐

#### 4.4.1 概要

自分の好きなアイドルの傾向から、関連するかもしれない他のアイドルをレコメンドする。
同じような好みを持った人が他に推している対象を提案することで、新しい推しとの出会いを創出する。

#### 4.4.2 アルゴリズム仕様

| ステップ | 処理内容 |
|----------|----------|
| 1. 類似ユーザー抽出 | 自分の推しリストとの重複が多いユーザーを集計 |
| 2. レコメンド候補算出 | 類似ユーザーが推している（自分は未登録の）アイドルをランキング |
| 3. スポット取得 | レコメンドされたアイドルの公開スポットをDBから取得 |
| 4. マップ表示 | 特別なピン（別色 or キラキラアイコン）でマップ上に表示 |

#### 4.4.3 表示仕様

| 項目 | 内容 |
|------|------|
| 表示場所 | マップ上に「おすすめスポット」として重ねて表示 |
| ピンデザイン | 通常ピンと区別できる別色/アイコン |
| ポップアップ | 「同じ好みのユーザー X 人が推しています」の理由テキスト |
| 実装方式 | シンプルなSQL集計（ML不要、Supabaseで完結） |

---

### 4.5 推しの言葉オーバーレイ機能（Phase F）⭐

#### 4.5.1 概要

スポットに登録された「推しの言葉」が、そのスポットに近づいたとき画面に降ってくる体験を提供する。
スポット詳細の写真に言葉を合成して保存することもできる。

#### 4.5.2 言葉の種類

| 種類 | 内容 |
|------|------|
| 投稿者が登録した言葉 | スポット投稿時に任意で記入できる言葉・コメント |
| プリセット言葉 | アプリが用意した定型フレーズ（「また来たよ」「ここにいたんだね」等） |

#### 4.5.3 機能仕様

| 機能 | 仕様 |
|------|------|
| 近接検知 | Web Geolocation API `watchPosition()` でリアルタイム監視、半径50m以内で発火 |
| アニメーション | CSS `@keyframes` で文字が上から降ってくる演出 |
| 写真合成 | Canvas APIでベース写真にテキスト合成、`toDataURL()`でダウンロード可能 |
| オーバーレイトグル | ON/OFFスイッチで元の写真も選択可能 |

---

### 4.6 重複投稿マージ（iOS Phase I限定）⭐

#### 4.6.1 概要

別のユーザーが同じ場所を投稿している場合、写真内のテキストを比較して同一スポットとして統合する。
Apple Intelligence の On-Device AIを使うことでプライバシーを保護しながら処理する。

#### 4.6.2 技術仕様

| 項目 | 内容 |
|------|------|
| OCRエンジン | `Vision.framework` の `VNRecognizeTextRequest`（On-Device） |
| 照合方法 | 抽出テキストをハッシュ化し、既存スポットの`ocr_text_hash`と照合 |
| 一致判定閾値 | テキスト一致率80%以上で「同一場所の可能性」として提案 |
| マージ動作 | 元投稿に訪問者として追加、写真は別エントリとして紐付け |
| プライバシー | On-Device処理のためサーバーに生テキストは送信しない |

## 8. 技術選定方針

### 8.1 段階的アプローチ

| Phase | 方針 |
|-------|------|
| Phase 1-2 | 開発速度優先、Vercel+Supabaseで最速構築 |
| Phase 3 | 安定性確保、本番運用に耐える構成 |
| Phase 4 | コスト最適化、必要に応じてホスティング移行 |

### 8.2 移行前提の設計

| 原則 | 説明 |
|------|------|
| **Vercel依存を避ける** | Vercel固有機能（KV、Blob等）は使用しない |
| **Supabaseに集約** | DB、Auth、Storageは全てSupabaseに統一 |
| **標準Next.js機能のみ** | どのホスティングでも動く構成 |
| **環境変数で設定外部化** | 移行時の変更を最小限に |

### 8.3 iOS版の技術選択

| 選択肢 | 採用 | 理由 |
|--------|------|------|
| **Swift + SwiftUI** | ✅ 第一選択 | ネイティブ機能（ジオフェンス等）に最適 |
| **React Native** | 予備 | Swiftが合わない場合の代替 |

## 10. 画像仕様

### 10.1 アップロード仕様

| 項目 | 仕様 |
|------|------|
| **ファイルサイズ上限** | 5MB/枚 |
| **枚数上限** | 4枚/投稿 |
| **対応形式** | JPEG, PNG, HEIC（iPhoneの標準形式） |

### 10.2 保存仕様

| 項目 | 仕様 |
|------|------|
| **保存形式** | WebP |
| **最大サイズ** | 1920px（長辺） |
| **圧縮品質** | 80% |
| **サムネイル** | 400px（長辺）、品質70% |
| **EXIF** | 削除（プライバシー保護） |

### 10.3 処理フロー

```
ユーザーが写真を選択
    ↓
1. EXIF情報を抽出（GPS座標・撮影日時）
    ↓
2. 抽出したデータをDBに保存
    ↓
3. 画像をリサイズ（最大1920px）
    ↓
4. WebPに変換（品質80%）
    ↓
5. EXIF情報を削除
    ↓
6. Supabase Storageにアップロード
    ↓
7. サムネイルを生成（400px、品質70%）
```
